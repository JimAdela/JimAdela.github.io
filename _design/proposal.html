诊断：不是不好看，是穿错了衣服

这站是 Hux Blog 的 fork，骨架、间距、配色全部来自 2016 年给图片博客设计的模板。八年过去，内容换了、读者换了，衣服没换。

问题分三层：可读性硬伤（有客观指标）、内容与形式错配（主观但致命）、工程债（顺手就能还）。

P0 可读性

首页摘要的对比度只有 2.5:1，不到及格线的一半

#A3A3A3 / 13px / 斜体，白底。WCAG AA 要求 4.5:1。而这段文字恰恰是读者决定"点不点开"的唯一依据——最该清楚的地方最糊。

P0 可读性

白字直接压在照片上，没有遮罩

文章页有 header-mask，首页和普通页没有。碰上浅色头图（如 post-bg-digital-native.jpg），标题几乎溶进背景。同一站两套规则，也是维护隐患。

P1 排版

给 800 字软文设计的节奏，现在跑 8000 字推导

正文 16px / 行高 1.7 / p{margin:30px 0}。中文长文在 1.7 行高下会显得拥挤，30px 段距又把它拉散——两头都不对。缺公式块、缺编号、缺图注。

P1 一致性

三套链接色打架

全局 a 是 #404040，正文内链接是 #337ab7，hover 又是 #0085a1。正文里的链接既无下划线也无足够色差，读者根本看不出哪是链接。

P1 架构

两条连载没有入口

「AI 数学直觉 25/52」「工程实战 3/30」是这站最值钱的资产，但站上只有 Home / About / Tags。读者没法连续追更，搜索引擎也拿不到系列关系。

P0 安全

Gitalk 的 clientSecret 明文渲染到前端

_config.yml 里的 secret 会原样进入每篇文章的 HTML。这不是优化项，是必须处理的事故——详见排期 P0。

P1 性能

Live2D 在 head 里同步加载，还和内容气质冲突

一个 <script> 阻塞首屏，背后拉一整套模型资源。jQuery 载了两次（CDN + 本地），Font Awesome 也载了两次。技术博客挂着会跳舞的看板娘，是 2016 年的浪漫，不是 2026 年的签名。

P2 细节

失修的小地方

英文日期夹在中文里、<html lang="en">、首页标题出现三次、空的 FRIENDS 区块仍在渲染、About 的文案还停在"PHP 程序猿，在杭州工作"。

主张：从「图片博客」改成「印刷讲义」

这个判断不是审美偏好，是从内容里读出来的。你的文章有章节号、有"六条诊断规则"、有定理式推导、有可照抄的配置——这是讲义的语法，不是日志的语法。

讲义有真实的视觉原型可依：页边批注、章节序号、图注与表注、纸面的微暖、单色印刷里那一处套色。它同时容纳数学（公式、编号、定理框）和工程（代码、清单、对照表），而照片墙容纳不了其中任何一样。

为什么不是暗色 暗色适合工具与仪表盘，不适合连续四十分钟读长文。它留到 P2 做可选主题，而不是默认。

三条原则，后面所有决定都从这里推出来：

  • 纸不白，墨不黑。底色取微暖的中性纸 #FCFBF8，正文用带一点绿调的近黑。二十万字的博客，降低的是长读疲劳，不是对比度。
  • 只有一处用色。套色绿只出现在"可交互"和"序号"上：链接、当前态、章节编号。看到绿色，就知道那里能点或那里是新的一节。朱色只做批注，全站面积不超过 2%。
  • 用规线，不用盒子。没有卡片、没有圆角、没有投影。分层靠 1px 细线和留白，像印刷品靠版心和对齐分层。

字：一个衬线，一个无衬线，一个等宽

中文网页字体动辄三到八兆，不能为主题下载宋体。所以策略是：让系统里已有的字各司其职。

标题走衬线（Noto Serif SC → 思源宋体 → 宋体 → Georgia），拿到印刷品的重量感；正文走系统黑体，保证可读与速度；日期、标签、章节号走等宽，把"数据"和"叙述"在视觉上分开。

段落与链接
批注 01 桌面端浮到版心右侧，移动端降级为左侧朱线块。这一条同时解决了"引用块满屏左边框"和"重要提醒没人看"两个问题。

大部分 GAN 教程停在"生成器骗判别器、判别器识破生成器"这个比喻上，然后直接贴两段 loss 代码。但比喻解释不了三个真问题：为什么 D 训到 50% 准确率反而可能是坏的？为什么生成器只会画一种数字？

读完这篇你能做到四件事：闭着眼睛推出最优判别器的形式，并说清它为什么是一个密度比；把极小极大目标化简成 Jensen-Shannon 散度；用一组数值实验量出梯度的消失点。

样张：真实文章套上新系统

用 10 月 29 日那篇 GAN 的开头，看看实际读起来是什么样。

第 25 章 / 52数学直觉2026-10-298 分钟

生成对抗网络：一场零和博弈的数学

直觉：造假币的人与验钞员

先看监督学习怎么工作。给一张图和一个标签，算交叉熵，梯度指向"让正确答案的概率更高"。目标函数是固定的、可微的、写死在那里的。

生成任务没有这个便利。要让模型生成一张猫的图片，"正确输出"是哪个像素矩阵？不存在。同一只猫可以有无数张照片，每一张都正确。你没法写出一个"像猫程度"的解析表达式。

判别器不是越准越好

反了。假设判别器一上来就完美，任何假样本都能以 0.999 的概率判假。此时生成器收到的梯度是 0——老师太强，学生连该往哪改都看不出来。

取舍：我故意没做的事

  • 没换 Hugo / Astro。站点只有 31 篇，Jekyll 在 GitHub Pages 上是零运维。迁移换来的是更快的构建，付出的是全部 URL 与评论的迁移成本——不值。
  • 没引入中文字体文件。宋体全量三兆起步，子集化又要随每篇文章重建。系统字体栈在 macOS 与 Windows 上都有合格的字，够用。
  • 没保留头图。它对"数学讲义"没有信息增量，只增加首屏重量。若你舍不得，P1 可以退一步：头图裁成 16:6 的窄带放在标题上方，而不是撑满全屏。
  • 没做卡片化。卡片适合条目同质、需要快速扫读的场景。这里是长文，卡片会把连续阅读切成碎片。
  • 编号只在真有序列的地方用。章节号用 CSS counter 自动生成，不手写 01/02/03 当装饰——那是最典型的模板痕迹。
